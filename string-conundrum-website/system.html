2The system

What we built, and how it works

String Conundrum is a React single-page application backed by a Flask API and PostgreSQL, deployed on a UCT Computer Science server. The browser presents; the server executes, traces and grades.

0Learning path

Eight modules, five stages each

Every module moves a learner from explanation to assessment in the same five stages. Passing a module's exam with at least 80% unlocks the next one; a setting allows free navigation, and a failed attempt points the learner back to practice on the concepts they missed.

  1. 0LearnShort explanations with code, callouts, tables and key points.
  2. 1ExamplesWorked examples stepped character by character.
  3. 2VisualiseThe module's operations play in the visualiser automatically.
  4. 3PracticeGenerated questions with misconception-linked feedback.
  5. 4ExamA paper drawn from a 276-question bank; 80% unlocks the next module.

Content is data. Each module is a content file rendered by shared components, chosen by each block's declared type, so a new module, exercise type or language needs new data rather than new rendering code. Lecturers can also create, reorder, publish and hide modules and exercises from their dashboard.

1Visualise

The String Visualiser

The visualiser is the part of the system that participants and reviewers rated highest. It exists as a standalone screen, open to guests, and inside every module's Visualise stage.

  • Six modes: slicing, index access, for loops, while loops, if statements and string methods.
  • Both index schemes at once. Positive and negative indices sit above and below the characters, and slice bounds are labelled start (inclusive) and stop (exclusive).
  • Played, not just drawn. Play, pause and speed controls, with spoken narration that waits for each sentence to finish before the next step.
  • Correct by construction. The engine is tested against 132 slice and 60 index expressions evaluated by CPython, and a failed evaluation is reported as an error instead of an empty selection.
  • Honest about limits. No major browser ships an isiXhosa voice, so selecting narration in isiXhosa explains the limitation instead of silently disabling the control.

2Experiment

Code Space

An editor and output panel for real Python, independent of the module sequence and open to guests. It returns output and errors but never assigns a mark, which keeps exploring separate from being assessed.

  • Server-side sandbox. Code runs in a fresh subprocess with a five-second wall-clock limit, restricted built-ins that remove imports, file access and dynamic execution, and a 64 MB memory cap on POSIX hosts such as the Linux server.
  • Step through your own code. An AST-based tracer replays the program statement by statement, up to 200 steps, with the characters each step touches highlighted.
  • States its scope. The visualiser pane says what it can trace, so unsupported code is never mistaken for an empty result.
  • isiXhosa on demand. A transpile control rewrites the editor's keywords into isiXhosa, with a banner confirming the switch.

3Practise

Practice, exams and misconception-linked feedback

  • Four question types: multiple choice, select-all, short answer and code writing. Code-writing answers are run as programs, so any correct solution earns credit.
  • Practice that does not run out. Each module composes questions from concept templates crossed with varied strings, question kinds, answer formats and difficulty tiers, so practice repeats without repeating itself.
  • Feedback that names the belief. Distractors are tied to named misconceptions where possible, and a worked-example panel shows the rule with the same character-cell highlighting as the visualiser.
  • Adaptive. The browser keeps a tally of the misconceptions a learner has hit, and the next question is weighted toward them without trapping the learner in one concept.
  • Tamper-proof grading. Each question carries a signed token, so the server recomputes the expected answer at grading time and rejects forged submissions. No answer key ever reaches the browser.

4Localise

English and isiXhosa

Localisation is part of the teaching, not a translated interface laid over it. Lessons, prompts, hints and feedback are available in isiXhosa, and learners may write Python keywords in isiXhosa too. The code the server runs is always standard Python.

Teaching content

Translated ahead of time

All eight modules were translated with the NLLB-200 model and the results committed, so no translation model runs on any request. Code fragments inside prose are masked before translation, and a check rejects any translation that alters them. Overlays apply field by field, so anything untranslated falls back to English instead of rendering blank.

Code

Transpiled deterministically

A 58-pair keyword table converts between English and isiXhosa keywords in the browser, longest phrase first and never inside strings or comments. The same table generates the learner-facing keyword reference, so the two cannot drift apart. Fifteen pre-translated templates explain the main runtime errors in isiXhosa.

Same 58-pair keyword table as the app

igama = "Python"

    bhala(igama[1:4])        # yth

    ukuba ch hayi ku "aeiou" kwaye ch != "y":
        bhala(ch, "is a consonant")

The demo uses the same keyword table, in the same order, as the app's transpiler; its output matched the original on every test program.

5Go further

Challenges, leaderboard and the lecturer dashboard

Challenges

18 coding problems

Seven easy, five medium and six hard problems, each with a hint, a worked solution and test cases. A submission runs against every stored test and counts only if all of them pass.

Leaderboard

Opt-in and private by default

Learners choose whether to appear and under what name, including anonymously. Standing is computed from recorded completions, never stored as a separate score that could drift.

Lecturer dashboard

Oversight without guesswork

Overview, Students, Marks, Analytics, Modules and Content, for the lecturer role only. Figures come from the server, and a value that was never recorded is shown as unrecorded, not as zero.

6Architecture

Presentation in the browser, authority on the server

Four decisions that shaped it

The browser never computes a mark. Grading, execution and lecturer analytics all happen on the server, so answer keys are never sent to the browser and there is only one grading implementation.

One execution language. isiXhosa keywords become Python before code leaves the browser, so the sandbox and tracer only ever see standard Python and its semantics stay exact.

Relational persistence. The proposal planned Firestore. PostgreSQL replaced it once progress, completions and leaderboards turned out to need aggregation and uniqueness constraints; Firebase kept only identity.

A frozen contract. The front-end and back-end interface was agreed before parallel development began and kept stable while each side evolved in response to evaluation.

7Request lifecycle

What happens when you press Run

  1. 0

    Transpile, if needed

    If the learner wrote isiXhosa keywords, the browser converts them to Python first. Nothing else is translated.

  2. 1

    Two requests in parallel

    POST /api/execute runs the program and POST /api/debug asks for its trace, issued together.

  3. 2

    Run in the sandbox

    A fresh subprocess with restricted built-ins, a five-second wall clock and a 64 MB address-space limit. A runaway loop is killed and reported as a timeout; it never blocks Flask.

  4. 3

    Trace the program

    The tracer parses the code once with Python's ast module and walks it statement by statement, recording the line, event, variables and the exact character indices each step touches.

  5. 4

    Explain a failure

    If execution failed and the learner works in isiXhosa, the matching error template is filled in, with details such as the line number.

  6. 5

    Render

    The browser turns each step into highlighted character cells and narration, with output and errors shown in visibly different states.
